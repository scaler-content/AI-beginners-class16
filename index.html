§ 1

Personal, Always-On, and Why Two

⏱ 12 min

Three words that get used loosely all the time. Each one means something specific, and each one costs something.

Personal agent

An agent that carries your context across sessions — your style, your projects, your prior conversations — instead of starting from zero every time. The word that matters is persistent, not private. A Gemini Gem is personal. It is not private in the sense of "on your disk."

Always-on

The agent is a process that keeps running when you're not looking at it — so it can be triggered by a timer or an incoming message at 11:40pm, not just by you typing. This is the part a browser tab can never do, and it's the entire reason OpenClaw runs a background service called the gateway.

Multi-agent system

Two or more agents with separate instructions, separate context, and a defined handoff between them. The separation is the whole product. Two prompts inside one conversation is not a multi-agent system — the second "agent" has already read, and been influenced by, everything the first one said.

📰
The newsroom analogy

Groundwire doesn't let reporters approve their own copy — and not because reporters are dishonest. It's because the person who wrote a sentence has already decided that sentence is right; that's why they wrote it. A sub-editor catches things the writer structurally cannot. Multi-agent systems are that org chart, in software. The reviewer agent isn't smarter than the researcher. It's just uncontaminated — it never saw the reasoning that produced the draft, only the draft.

The orchestrator + sub-agent shape

Almost every multi-agent system you'll meet is one of two shapes, and it's worth being able to name them out loud:

ShapeHow it runsGood for
Pipeline (handoff)Agent A finishes, writes its output somewhere, Agent B picks it up. Fixed order.Draft → review. Research → write. Anything with a clear "then".
Orchestrator + sub-agentsA manager agent decides at runtime which specialists to spawn, and how many.Jobs where you don't know the sub-tasks until you've read the request.

Today you're building the pipeline shape — researcher hands to reviewer, every time, in that order. The orchestrator shape gets a proper look in §4, because OpenClaw supports it natively, but we are deliberately not building it. A fixed handoff you can debug beats a dynamic one you can't.

The five parts of an always-on personal agent — gateway, skills, memory, heartbeat, and the model. Only the last one lives in the cloud.

The five parts, in plain words

PartWhat it doesWhy you care today
GatewayThe background service that receives messages and routes them to an agentThis is what "always-on" actually is. It's also what routes to agent #1 vs agent #2.
SkillsThe tools the agent can reach for — web search, reading and writing filesWriting a file is how our two agents hand work to each other.
MemoryPlain Markdown files in a workspace folder on your diskOpenable, greppable, backup-able. And separate per agent by default.

Zara asks her single research agent to write a brief, then in the very next message asks it: "now review that brief critically and flag anything unsupported." Is that a multi-agent system?

AYes — two distinct tasks were performed, so there are effectively two agents.
BNo — the reviewer shares the writer's context, so it inherits the same assumptions it's supposed to catch.
CYes, as long as the second message uses the word "critically".
DNo — multi-agent requires the two agents to run on different machines.
Answer: B. The separation that makes a review worth anything is context separation, not task separation. In one conversation, the "reviewer" can see every step of reasoning that produced the draft — including the shaky leap it should be flagging — and that reasoning reads as justification, not as evidence. This is the single most common fake multi-agent setup, and it's fake in a way that's hard to notice because the output looks like a review. Different machines have nothing to do with it (D): the reviewer we build today runs on the same laptop as the researcher. It just can't see inside its head.

Build 1 — Your Gem in Ten Minutes

⏱ 10 min

No terminal, no install, no API key, no card. This is Advait's phone agent — and it's everyone's safety net for the rest of today.

🎙 Instructor Says

"Before we touch a terminal, everyone in this room is going to have a working personal agent. Ten minutes, browser only. I'm doing it this way for a very practical reason: the next build involves installing software on twenty different laptops, and I have never once seen that go perfectly for everyone. If your OpenClaw install fights you later, you still built an agent today."

Gem

Google's name for a saved, reusable set of instructions inside the Gemini app — a custom assistant you configure once and then open like a contact. Instructions plus optional reference files. Free on every Gemini plan, including the free tier — no Pro or Ultra needed.

Why a Gem replaces the messaging bot: the original version of this class connected the agent to Telegram. We cut it. A bot needs registration with @BotFather, a token, and a fiddly rule about who has to message whom first — and it puts a second app on everyone's phone. A Gem does the same job Advait actually needed (his agent, on his phone, wherever he is) with a Google account he already has. When you see "Telegram" in an agent tutorial, ask what job it's doing. Usually the job is reachability, and there's a cheaper way to get it.
  1. Open gemini.google.com on a computer and sign in with a personal Google account. Creating and editing Gems is web-app only — the mobile app can use them but not build them.
  2. In the left sidebar, find Explore Gems, then click New Gem. If your sidebar is collapsed, expand it with the ☰ icon first.
  3. Give it a name. Ours: Groundwire Desk Editor.
  4. Paste the instructions from the panel below into the Instructions box. Read it out loud as you paste — every line in it is doing a job.
  5. (Optional) Under Knowledge, click Add files and upload a style guide or a couple of past articles. Up to 10 files, 100 MB each. This is what makes it Groundwire's editor rather than a generic one.
  6. Click Save. Open it from the sidebar and paste in a rough paragraph to see it work. The Gem now also appears in the Gemini mobile app under the same account.

Name
Groundwire Desk Editor
Instructions
You are the desk editor for Groundwire, a small digital newsroom. When I paste rough copy or a field note, do exactly this, in this order: 1. Rewrite it as a tight news paragraph, maximum 90 words, plain language, no adjectives doing the work of facts. 2. List every factual claim you found, as bullets. 3. For each claim, mark it VERIFIED, NEEDS SOURCE, or UNSUPPORTED. Never guess a source — if I did not give you one, it is NEEDS SOURCE. 4. Rules you never break: - Never invent a name, a number, a date, or a location. - If the note is too thin to write from, say so and ask for the missing piece instead of filling the gap. - Keep my wording where it is already good. You are editing, not rewriting for sport.
Knowledge (optional)

✓ What the Gem gives you

Reusable instructions you configure once. Reference files it reads every time. Works on web, phone, and the Gemini side panel. Free. Ready in ten minutes. Genuinely useful for the 80% case.

✗ What it can't do

It can't run when you're not there — no timer, no incoming trigger. It can't read or write files on your laptop. Its memory of your conversations isn't a file you own. And it's one agent: it can't hand work to a colleague.

That right-hand column is not a criticism of Gems — it's a specification for the next build. Every single one of those four gaps is something the next section closes.

Advait wants his Gem to check tips against Groundwire's house style automatically at 6am each day, before he wakes up. What's the honest answer?

AAdd "run this every morning at 6am" to the Gem's Instructions.
BUpload a schedule file under Knowledge and the Gem will follow it.
CA Gem can't do it — it only runs when a human opens it and types. Scheduling needs something always-on.
DIt works if he leaves the Gemini tab open overnight.
Answer: C. A Gem is a saved configuration, not a running process. There is nothing there to wake up. Instructions describe how to respond when someone talks to it — they can't cause it to start talking. This is exactly the personal-vs-always-on distinction from §1, and it's the specific gap the gateway in the next build fills. Option D is the tempting one: an open browser tab feels like something running, but the tab is just a window onto a service that only acts when prompted.

Build 2 — OpenClaw on Your Machine

⏱ 20 min

Same idea as the Gem — a personal agent — but this one is a process running on your hardware, with memory you can cat.

Instructor — before you teach this live: run the entire install on a clean machine (or a fresh user account) the night before, and screenshot every wizard screen as it exists this week. OpenClaw ships fast and wizard wording moves. Also decide your fallback now: if more than a third of the room is stuck at the ten-minute mark, stop, demo the rest from your screen, and hand them §7's install checklist as homework. Build 1 working for everyone beats Build 3 working for four people.

What OpenClaw actually is

An open-source agent runtime you install on your own computer. It gives you the four things a Gem couldn't: a background service that keeps running, tools that reach your filesystem and the web, memory stored as Markdown files in a folder you own, and — the reason we're here — the ability to run more than one agent, each with its own workspace and its own instructions.

You still rent the thinking. The model is Gemini, over the free API tier, reached by a key. What you stop renting is everything around it.

Renting a furnished flat versus owning the place. Both are legitimate choices — they're just different failure modes.

Step 1 — Get a free Gemini API key

  1. Go to aistudio.google.com and sign in with a Google account.
  2. Click Get API key (top right), then Create API key. Let it create a project if it offers.
  3. Copy the key — it starts with AIza. Park it in a notes file for the next two minutes.
  4. While you're there, open aistudio.google.com/rate-limit and look at your own live limits for the model you plan to use.
AI Studio → Get API key. No credit card, no billing account.
Read this before you quote a number at your class: Google cut free-tier daily request limits sharply in December 2025, and the ceilings have moved several times since — different models now sit at wildly different daily allowances, and older tutorials confidently quoting "1,500 requests a day" are simply out of date. Don't teach a number from memory or from this script. Open the rate-limit page in AI Studio on the day and read what your account actually has. The teaching point survives regardless: free tiers are metered, the meter moves, and twenty students sharing a classroom Wi-Fi find the ceiling much faster than one person at home.

If that makes you uncomfortable, the npm line does the same job." Don't skip this. Half the room has copy-pasted a curl-to-bash before without ever thinking about it.

Build 3 — The Second Agent

⏱ 24 min

Priya's ask, built. One new command, one new folder, one file that passes between them — and a reviewer that has never seen the researcher's reasoning.

🎙 Instructor Says

"Notice how small this build is. We are not installing anything new. We're not adding a framework with 'orchestration' in the name. We add one agent with one command, give it a different job description, and point both of them at one file. That's the whole multi-agent system."

"If that feels anticlimactic — good. Most of the complexity people associate with multi-agent systems is complexity they chose. The idea underneath is genuinely this small."

Step 1 — Add the reviewer

terminal
$ openclaw agents add reviewer
✓ agent reviewer created
  workspace  ~/.openclaw/workspace-reviewer
  state dir  ~/.openclaw/agents/reviewer/

$ openclaw agents list --tree
main      (default)  ~/.openclaw/workspace
reviewer              ~/.openclaw/workspace-reviewer

That one command gave the reviewer its own workspace, its own state directory, and its own session store. They are separate by default — which is exactly the property Priya is buying. The reviewer does not inherit the researcher's memory, its notes, or its conversation history.

◆ Agent 1

main — the researcher

Searches, reads, and drafts. Optimistic by design: its job is to find and assemble the story. Writes its draft to a file and stops.

~/.openclaw/workspace
◆ Agent 2

reviewer — the sub-editor

Never searches, never drafts. Reads the file cold, hunts for unsupported claims and disagreeing sources, and writes a verdict beside it.

~/.openclaw/workspace-reviewer

Step 2 — Give each one its job description

An agent's standing instructions live in AGENTS.md in its own workspace. Open each in a text editor. The researcher's:

~/.openclaw/workspace/AGENTS.md
# Role: Groundwire researcher

When I ask you to research a topic:
1. Search the web and read the best 3-5 sources.
2. Write a brief: summary, key claims as bullets, then a Sources list with links.
3. Beside every claim, name which source it came from.
4. Save it to ~/groundwire/briefs/<topic>.md
5. Reply with the file path. Do not self-assess. Someone else reads it.

And the reviewer's — note how much of it is about what not to do:

~/.openclaw/workspace-reviewer/AGENTS.md
# Role: Groundwire sub-editor

You review briefs. You do not write them and you do not research.

Given a file path, read it and produce, for every claim:
  KEEP    - supported by a named source
  FLAG    - sources disagree, or the source does not say this plainly
  CUT     - no source at all, or the source does not exist

Then: list any claim where two sources genuinely conflict, and say
what a reader would need in order to decide between them.

Rules:
- Never add a fact. If the brief is thin, that is a finding, not a gap to fill.
- Never soften a CUT because the writing is good.
Save your verdict to <same-path>-review.md

Step 3 — The handoff

Here is the nuance that matters, and it's worth slowing down for. Each agent's workspace is its default working directory — not a locked sandbox. Relative paths stay inside the workspace; an absolute path can reach outside it. That's why both job descriptions above use an absolute path, ~/groundwire/briefs/, that sits outside either workspace.

🔎 main
researches, drafts
──▶
~/groundwire/briefs/
flood-warning.md
──▶
🔍 reviewer
reads cold, judges
──▶
…-review.md
🗄️
Why a shared folder, not shared memory

The file is the handoff, and that's a deliberate design choice rather than a limitation. If you gave both agents one shared memory store, the reviewer would start absorbing the researcher's working notes — its half-formed theories, its "this source seems dodgy but let's go with it" — and you'd be right back to marking your own homework. A file is a narrow, inspectable doorway: exactly the finished draft passes through, and nothing else. OpenClaw's own docs make the same argument, recommending separate memory by default with sharing added only where you can point at the reason.

The two-terminal demo: run this with two terminal windows side by side on the projector, one per agent, so the room can literally see there is no shared conversation between them. Left window asks main to research; it prints a path. Right window pastes that path to reviewer. The reviewer's very first sight of the topic is the file.
terminal — the full round trip
$ openclaw --agent main "Research how flood early-warning
    systems are funded in Indian cities. Brief only."
✓ wrote ~/groundwire/briefs/flood-warning-funding.md

$ openclaw --agent reviewer "Review
    ~/groundwire/briefs/flood-warning-funding.md"
✓ wrote ~/groundwire/briefs/flood-warning-funding-review.md

$ cat ~/groundwire/briefs/flood-warning-funding-review.md
KEEP  central scheme funding, named in source 2
FLAG  "most cities" - source 1 says most, source 3 says a third
FLAG  2024 figure - source 2 is quoting a 2021 report
CUT   "widely considered successful" - no source states this
Beginner Note — flags are the point, not a failure. A review that comes back with nothing flagged usually means the reviewer isn't reviewing. When your reviewer produces all KEEPs on the first run, don't celebrate — suspect the instructions. The most common cause is an AGENTS.md that describes the reviewer as "helpful", which quietly pushes it toward agreeing with you.

The other shape: orchestrator + sub-agents — concept only, we are not building this

What you just built is a fixed pipeline: you decide the order. OpenClaw also supports the dynamic version, where one agent spawns others at runtime by calling a sessions_spawn tool, and you can inspect who spawned whom with openclaw agents list --tree. Agents created that way are marked as agent-created and need operator approval before they run.

We're not building it today, for a reason worth stating plainly. A spawning orchestrator is genuinely harder to debug: when the output is wrong you now also have to work out which agents existed, why the manager decided to create them, and what each was told. Build the fixed pipeline first. Reach for orchestration when you can name a job where you honestly don't know the sub-tasks until you've read the request — and if you can't name one, you don't need it yet.

⚡ Simulator 3 — You Are the Reviewer

Three sources. They don't agree. Judge each claim in the draft brief — KEEP, FLAG, or CUT — and watch the brief rewrite itself as you go. Then compare with what the reviewer agent produced.

A team gives the researcher and the reviewer one shared memory store, "so the reviewer has full context." What breaks?

ANothing — more context always produces a better review.
BThe two agents will overwrite each other's files and crash the gateway.
CThe reviewer inherits the researcher's reasoning, so it judges the draft against the same assumptions that produced it.
DNothing breaks, but it uses twice the disk space.
Answer: C. The reviewer's value is that it arrives cold. Once it can read the researcher's working notes, a shaky claim no longer looks shaky — it arrives pre-justified, wrapped in the reasoning that produced it, and reads as settled. You've rebuilt the single-agent setup with extra steps and a more confident tone. This is why OpenClaw isolates agent memory by default and treats sharing as the exception you have to argue for. And note what the wrong answers get wrong: nothing technical fails here (B, D). That's what makes it dangerous — the system keeps working perfectly while quietly producing worthless reviews.
§ 5

Giving It Hands — the n8n Webhook

⏱ 10 min

The reviewer's verdict is a file on Zara's laptop. Priya can't read it there. This is the last hop — and it's the one where credentials matter.

Thinking and doing are different jobs, and they want different tools.

Three reasons to hand the last step to n8n

ReasonWhat it means here
🔒 Credentials stay putGroundwire's Google account lives in n8n, not in the agent. If someone talks the agent into something stupid, the worst it can do is call a webhook. It has no way to read the newsroom's mail.
⚡ Don't pay a model to do plumbingCreating a Google Doc is an API call with a known shape. There is no reasoning in it. Every token spent on it is wasted.
✅ Same input, same outputAn n8n workflow does the identical thing every run. Model output varies by design. Put the parts that must not vary where they can't.
Webhook

A URL that does something when data is posted to it. You hand the address out; whoever has it can drop a package there. Our agent finishes a review and posts the result to n8n's address — it doesn't need to know, or be trusted with, what happens next.

Agent reasons, webhook carries, n8n acts — with the credentials on the far side of the wall.
  1. In n8n (your instance from Class 11, or a free cloud account), add a Webhook node. Method POST. Copy the URL it gives you.
  2. Add a Google Docs → Create Document node. Title: Review: {{ $json.topic }}. Content: {{ $json.verdict }}.
  3. Add a Gmail → Send Email node addressed to Priya, so the sub-editor's verdict reaches an actual sub-editor.
  4. Add a Respond to Webhook node so the agent gets a confirmation back rather than silence.
  5. Activate the workflow, then test it from a terminal with curl before the agent ever touches it. If the Doc doesn't appear from curl, the agent isn't your problem.
test the workflow before wiring the agent

Why put Google credentials in n8n rather than in the agent, when the agent is running on your own laptop anyway?

AOpenClaw has no way to store credentials.
BSo that the blast radius of a manipulated or malfunctioning agent stops at "posted junk to a webhook".
CBecause Google requires credentials to be held by an automation platform.
DIt's faster, since n8n caches the login.
Answer: B. Least privilege: each component holds only what it strictly needs. The agent needs the ability to trigger the email — not the ability to read the mailbox, and those are very different powers that a stored password would bundle together. "It's my own laptop" isn't the safeguard people think it is, either: the risk isn't someone stealing the machine, it's the agent reading a web page that contains instructions aimed at it. Narrow the permissions and that stops being a crisis.
§ 6

When Two Agents Is the Wrong Answer

⏱ 14 min

The section every multi-agent tutorial leaves out. You've just built one — now here's when not to.

🎙 Instructor Says — say this exactly

"Multi-agent is the most over-applied idea in this entire course. It's genuinely useful, and it sounds impressive in a demo, and those two facts together mean people reach for it constantly for jobs that a single prompt would have done better, faster, and more reliably."

"So here's the rule I want you to leave with. Every agent you add is a handoff, and every handoff is a place where meaning gets lost and something can break. You need to be able to say what the second agent is buying you. If the answer is 'separation' — like Priya's reviewer — that's a real answer. If the answer is 'it felt more organised', you've bought yourself latency and a bigger bill."

✗ Not justified

"Summariser agent" → "formatter agent"

Two agents for what is genuinely one instruction. Twice the latency, twice the calls, and a new failure mode — the formatter misreading the summariser — bought for nothing. One prompt with two numbered steps does this better.

✗ Not justified

A "manager agent" over two fixed steps

If the order never changes, you don't need something deciding the order at runtime. You've replaced a reliable arrow with a coin flip and paid a model call for the privilege.

✓ Justified

Writer → reviewer (today's build)

The second agent exists precisely because it must not see what the first one saw. Context separation isn't a side effect here; it's the entire product. No single-prompt version gets you this.

✓ Justified

Different tools, different permissions

One agent may read the newsroom's inbox; another may publish to the site. Splitting them keeps a mistake in one from becoming a mistake in the other — the same argument as putting credentials in n8n.

The three costs, stated plainly

CostHow it growsThe bit people forget
MoneyRoughly linear — each agent is its own model callsThe handoff isn't free either: agent two re-reads the whole draft as input every single time.
LatencyAdditive in a pipeline — the stages can't overlapA review that takes 40 seconds is fine nightly, and unusable in a live chat.
ReliabilityMultiplicative — and this is the one that bitesFour steps at 95% each is 81% end-to-end, not 95%. Nobody plans for that number.

A five-agent pipeline where each agent succeeds 95% of the time. What fraction of runs complete without any step failing?

A95% — each agent is independently reliable.
BAbout 77% — the per-step rates multiply.
CAbout 19% — 95% divided across five steps.

Answer: B. 0.95⁵ ≈ 0.774. A one-in-twenty failure rate per step sounds tolerable right up until you chain five of them and roughly a quarter of your runs are broken. This is the actual argument against casually adding agents — not the money, which is usually small, but the compounding. It's also the argument for the reliability settings you met in Class 15: retries and iteration caps raise each individual step's number, and because these multiply, lifting each step from 95% to 99% takes the five-stage pipeline from 77% to 95%.
§ 7

Take-Home — Build It Yourself

⏱ 6 min

Three challenges, one per build. Nothing here needs a tool you didn't open today.

C1

Your own Gem, for something you actually do weekly

▸
Mission

Pick a task you repeat — reviewing pull requests, writing standup updates, drafting replies to a certain kind of email. Build a Gem for it, with the same four-part shape as the Desk Editor: what to produce, in what order, what to mark as uncertain, and a hard list of things it must never invent.

Done when

You've used it three separate times without editing the instructions, and it's on your phone. If you find yourself re-explaining the same thing in every chat, that thing belongs in the Instructions box — go put it there.

Stretch

Add a Knowledge file and find one answer that measurably changed because of it.

C2

Finish the OpenClaw install and teach it about you

▸
Mission

If the install didn't complete in class, finish it: Node check → install → openclaw onboard --install-daemon → openclaw doctor → openclaw dashboard. Then teach it five true things about how you work, end the session, and come back the next day.

Done when

You can open ~/.openclaw/workspace/USER.md and read those five things as text — and you've edited one of them by hand, then confirmed in chat that the agent picked up your edit.

Stretch

git init the workspace folder and commit it. Your agent's memory now has version history, and you can diff what it learned this week.

C3

Add a second agent that disagrees with the first

▸
Mission

openclaw agents add critic. Give it an AGENTS.md whose entire job is to find the weakest claim in whatever it's handed, in a domain you know well enough to judge it. Have agent one write to a shared folder; hand the critic the path.

Done when

The critic has caught at least one thing you agree with — and you've written down one thing it flagged that was wrong. Both halves matter. An agent you never disagree with isn't being read carefully.

The real question to answer in writing

Two sentences: was the second agent worth it for this job, or would a single well-written prompt have done the same? Say why. Getting to "no, it wasn't worth it" is a completely valid outcome — that judgement is the actual skill this class is teaching.

If you set one of these as graded homework: C1 and C2 are safe for everyone. C3 depends on C2 completing, so either make it optional or pair it with a "describe what you would build" written alternative for anyone whose machine wouldn't cooperate.

Key Takeaways

Personal, private, and always-on are three different things. A Gem is personal. OpenClaw is personal and private and always-on. Knowing which one a job needs saves you an install you didn't have to do.

Memory as files is the whole argument for running it yourself. You can read why it believes something, fix it with a text editor, and put it in git. None of that is possible with memory you can't open.

The separation is the multi-agent system. Two prompts in one conversation is not two agents. If the reviewer can see the writer's reasoning, it isn't reviewing.

A file makes a better handoff than shared memory. A narrow, inspectable doorway that passes exactly the finished draft — and none of the working notes that would contaminate the review.

Reliability multiplies, and that's the real cost of another agent. 0.95⁵ ≈ 77%. Money and latency you can budget for. Compounding failure is the one that surprises people.

Give the agent the trigger, not the keys. Its worst possible day should be short to describe. Ours: it posts junk to one webhook.
